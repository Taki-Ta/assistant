# 面经 AI 助手：需求与验收标准

## 1. 项目目标

构建一个可以读取本地 Markdown 面经资料、回答问题并标注证据来源的 AI 助手，
同时支持生成模拟面试题和评价用户答案。

项目完成后应能证明以下能力：

1. 使用 Python 构建可测试、可维护的 AI 后端。
2. 理解 LLM 请求、流式输出、结构化输出和工具调用。
3. 独立实现一条 RAG 链路，而不是只会调用封装框架。
4. 使用固定评测集量化检索和回答质量。
5. 记录延迟、Token 用量、错误和模型调用成本。

## 2. 目标用户与场景

主要用户是正在准备技术面试的开发者。

核心场景：

- 从本地面经中查询某项技术知识。
- 查看回答对应的来源文件与原文片段。
- 按岗位、技术方向和难度生成面试题。
- 提交自己的回答，获得结构化评分和改进建议。

## 3. MVP 范围

### FR-01 文档采集

- 递归扫描配置目录中的 `.md` 文件。
- 排除 `.git`、`.venv`、缓存目录和项目自身生成文件。
- 保存文件路径、标题、修改时间和内容摘要等元数据。
- 文件内容变化后只重新处理发生变化的文件。

验收标准：

- 对测试资料集中的可读 Markdown 文件采集覆盖率达到 100%。
- 重复执行采集不会产生重复文档或重复片段。
- 单个文件损坏时记录错误，但不阻断其他文件处理。

### FR-02 文档切块与索引

- 优先按照 Markdown 标题和段落切块，超长内容再按长度切分。
- 每个片段保留文件路径、标题层级和片段编号。
- 为片段生成 Embedding，并写入向量存储。
- 支持完整重建与增量更新索引。

验收标准：

- 任一检索结果都能定位回原文件和原文片段。
- 在至少 30 个问题的评测集上，`Hit@5 >= 80%`。
- 索引同一批文件两次，片段总数保持一致。

### FR-03 有依据的问答

- 根据用户问题检索相关片段，再调用模型生成答案。
- 没有足够证据时明确说明资料不足，不编造答案。
- 回答必须包含引用，至少给出来源文件和片段编号。
- 支持流式输出。

验收标准：

- 评测集中引用有效率达到 95%：引用确实存在且能定位原文。
- 人工抽查 20 个回答，关键结论有证据支持的比例达到 90%。
- 无相关资料的问题中，至少 90% 能正确拒答或声明不确定。

### FR-04 模拟面试

- 按岗位方向、难度和题目数量生成问题。
- 支持用户提交回答。
- 返回结构化结果：总分、知识准确性、完整性、表达、遗漏点和参考答案。
- 评分范围固定为 0～100，并给出评分依据。

验收标准：

- 相同评分规则下，输出字段解析成功率达到 100%。
- 每个扣分项都包含具体原因，而不是只返回分数。
- 生成的问题至少包含来源或明确标记为模型扩展题。

### FR-05 HTTP API

MVP 至少提供以下接口：

```text
POST /documents/index       建立或更新索引
POST /chat                  非流式问答
POST /chat/stream           流式问答
POST /interviews/questions  生成面试题
POST /interviews/evaluate   评价回答
GET  /health                健康检查
```

验收标准：

- FastAPI 自动生成 OpenAPI 文档。
- 请求和响应全部使用 Pydantic 模型。
- 参数错误返回 4xx，内部或模型错误返回合适的 5xx，不泄露密钥和堆栈。
- 核心接口具有正常、边界和异常测试。

### FR-06 会话与可观测性

- 保存会话、问题、回答、引用和创建时间。
- 每次模型调用记录模型名、耗时、输入/输出 Token 和调用状态。
- 日志包含请求 ID，且不记录 API Key。

验收标准：

- 可以按请求 ID 找到一次请求的完整处理记录。
- Token 统计字段覆盖所有模型调用。
- 自动化测试确认日志和 API 响应中不出现密钥。

## 4. 非功能需求

### NFR-01 可维护性

- 使用 `src/interview_ai` 包结构。
- 对外函数和 API 模型使用类型注解。
- 模型供应商、Embedding 和向量存储通过接口隔离。
- 第一版直接使用模型官方 SDK，不引入 LangChain。

### NFR-02 质量门禁

- `uv run pytest` 全部通过。
- `uv run ruff check .` 全部通过。
- `uv run ruff format --check .` 全部通过。
- 核心业务代码测试覆盖率目标不低于 80%。

### NFR-03 性能与稳定性

- 除外部模型耗时外，单次检索 P95 小于 500 ms（以本地评测环境为准）。
- 模型调用设置连接超时、总超时和有限次数重试。
- 同一个索引任务不能并发重复执行。

### NFR-04 安全

- 密钥只从环境变量读取，`.env` 不进入 Git。
- 上传或配置的路径必须限制在允许的数据目录内。
- 检索到的文档内容视为不可信输入，不能直接当作系统指令执行。

## 5. 暂不实现

以下内容不属于 MVP，避免学习范围失控：

- 自己训练或微调大模型。
- 多 Agent 协作框架。
- Web 前端和移动端。
- Kubernetes、Kafka、Celery 等分布式基础设施。
- 同时适配多个向量数据库。
- 语音、图片和视频等多模态输入。

## 6. 建议技术选型

- Python 3.12（优先保证 AI 生态兼容性）
- FastAPI、Pydantic、httpx 或模型官方 SDK
- SQLite 保存会话和评测数据
- Qdrant 或 PostgreSQL + pgvector（二选一，不同时学习）
- pytest、pytest-cov、Ruff、uv

## 7. 最终完成定义

只有同时满足以下条件，MVP 才算完成：

1. FR-01 至 FR-06 的验收项全部通过。
2. 至少 30 个问题的评测集已提交到仓库。
3. `Hit@5 >= 80%`、引用有效率 `>= 95%`、有依据回答比例 `>= 90%`。
4. 自动化测试、Ruff 和格式检查全部通过。
5. README 包含安装、配置、运行、测试、评测和架构说明。
6. 项目能在一台新机器上按照 README 从零启动。
