>

## 1. 项目概览

该项目是一个基于用户知识库的 Python AI 后端。目前已经形成以下主链路：

1. 扫描本地 Markdown 文件，读取文件元数据与正文。
2. 按 Markdown 标题、段落和最大字符数切块。
3. 用 OpenAI Embedding API 批量生成向量。
4. 将文档、Chunk 和向量写入 PostgreSQL + pgvector。
5. 通过 pgvector 的余弦距离完成向量检索；同时保留内存向量库用于测试。
6. 通过 FastAPI 暴露文档上传、列表、索引与健康检查接口。
7. 使用 JWT Bearer Token 区分用户数据。
8. 使用 Typer 提供扫描与索引变更预览 CLI。
9. 通过 Responses API 和本地知识检索工具提供普通及 SSE 流式 RAG 问答，持久化会话、Turn、完整消息、工具事件与历史摘要。
10. 用 Token 估算和预算构建上下文，超限时压缩较早历史，并按剩余容量限制检索结果。

从代码结构看，项目采用 `src` 布局，并按 `api`、`agent`、`db`、`ingestion`、`indexing`、`evaluation` 分层。Embedding、Chunk 存储与向量存储通过 `Protocol` 抽象，核心索引服务依赖接口而不是具体实现，便于测试和替换基础设施。

#### 3.1.1 `lifespan` 与 `request.app.state`

FastAPI 的 `lifespan` 用来管理“随应用启动而创建、随应用关闭而释放”的资源，例如 HTTP 客户端、模型客户端、连接池和无状态 Provider。它由 `@asynccontextmanager` 定义：

- `yield` 之前的代码在应用启动时执行；
- `yield` 期间应用接收和处理请求；
- `yield` 之后的代码在应用关闭时执行。

`app.state` 是当前 FastAPI/Starlette 应用实例上的共享状态容器。`Request` 是请求级对象，而 `request.app` 指向处理该请求的应用实例，因此可以通过 `request.app.state` 取得应用启动时创建的共享资源：

```text
应用启动
  └─ lifespan 创建 AsyncOpenAI 和 embedding_provider
       └─ 保存到 app.state.embedding_provider
            ├─ 请求 A 通过 request.app.state 取得它
            ├─ 请求 B 通过 request.app.state 取得它
            └─ 应用关闭时释放 AsyncOpenAI
```

项目当前在应用生命周期内创建并关闭客户端：

```python
from collections.abc import AsyncIterator
from contextlib import asynccontextmanager

from fastapi import FastAPI
from openai import AsyncOpenAI


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    async with AsyncOpenAI(
        api_key=config.api_key,
        base_url=config.host,
    ) as client:
        app.state.embedding_provider = OpenAIEmbeddingProvider(
            client=client,
            model=config.embedding_model_name,
            dimensions=config.dimensions,
        )
        yield


def create_app() -> FastAPI:
    return FastAPI(lifespan=lifespan)
```

`async with` 会在正常关闭和异常退出时调用客户端的异步清理逻辑。如果不使用客户端的上下文管理器，也可以显式关闭，但必须放在 `finally` 中：

```python
@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    client = AsyncOpenAI(
        api_key=config.api_key,
        base_url=config.host,
    )

    try:
        app.state.embedding_provider = OpenAIEmbeddingProvider(
            client=client,
            model=config.embedding_model_name,
            dimensions=config.dimensions,
        )
        yield
    finally:
        await client.close()
```

不要只写 `yield` 后直接 `await client.close()` 而省略 `try/finally`。当生命周期内出现异常时，`finally` 才能明确保证资源释放。

##### 通过 FastAPI 依赖注入读取共享资源

业务路由不应到处直接访问 `request.app.state`。项目在 `dependencies.py` 中集中定义一个访问函数，再让其他依赖使用它：

```python
from typing import Annotated

from fastapi import Depends, Request


def get_embedding_provider(request: Request) -> OpenAIEmbeddingProvider:
    return request.app.state.embedding_provider


EmbeddingProviderDependency = Annotated[
    OpenAIEmbeddingProvider,
    Depends(get_embedding_provider),
]


def get_search_service(
    db: DatabaseSession,
    embedding_provider: EmbeddingProviderDependency,
) -> SearchService:
    return SearchService(
        embedding_provider=embedding_provider,
        vector_store=PostgresVectorStore(db),
    )


def get_index_service(
    db: DatabaseSession,
    embedding_provider: EmbeddingProviderDependency,
) -> IndexService:
    return IndexService(
        embedding_provider=embedding_provider,
        chunk_store=PostgresChunkStore(db),
        vector_store=PostgresVectorStore(db),
    )
```

这里的生命周期分工是：

| 对象 | 生命周期 | 原因 |
|---|---|---|
| `AsyncOpenAI` | 应用级 | 内部 HTTP 连接池可以被多个请求复用，应用关闭时统一释放 |
| `OpenAIEmbeddingProvider` | 应用级 | 只封装共享客户端和固定模型配置，本身不保存用户或请求状态 |
| `SearchService` / `IndexService` | 请求级 | 每次注入当前请求的数据库 session，但内部复用同一个 embedding provider |
| `ConversationService` | 请求级 | 编排会话持久化、短事务和模型调用，不跨请求保存状态 |
| `AsyncSession` | 请求级 | 事务边界属于单个请求，不能被并发请求共享 |
| `AgentContext.owner_id` | 请求级 | 来自当前请求 Token 的 `sub`，必须按用户隔离 |

因此，`SearchService` 和 `IndexService` 可以共用同一个 embedding provider，但不能把带有当前 `AsyncSession` 的 service 直接放进 `app.state`。`owner_id` 也不应放进 `app.state`，否则并发请求可能互相覆盖用户信息。

##### `app.state` 的范围和注意事项

1. `app.state` 是“每个应用实例/进程一份”，不是整个集群共享的数据。启动多个 Uvicorn/Gunicorn worker 时，每个 worker 都会创建自己的客户端和 provider。
2. 放入其中的对象必须适合并发使用。OpenAI 异步客户端及其连接池适合请求间复用；数据库 session、请求对象和用户上下文不适合。
3. `state` 的属性是动态添加的，类型检查器无法自动知道属性是否存在。应集中通过 `get_embedding_provider()` 访问，避免业务代码散落 `request.app.state.xxx`。
4. 不要在模块导入时直接创建需要关闭的客户端。模块级对象没有清晰的启动/关闭边界，也会让测试替换依赖更困难。
5. 测试生命周期资源时，应把 `TestClient` 当作上下文管理器使用，确保 startup 和 shutdown 都会执行：

```python
app = create_app()

with TestClient(app) as client:
    response = client.get("/health")
    assert response.status_code == 200
```

普通业务测试仍可以使用 `app.dependency_overrides` 替换 `get_embedding_provider`、`get_search_service` 或 `get_index_service`，避免调用真实 OpenAI API。

##### `__enter__`、`__exit__` 与 `close()`

Python 使用上下文管理器表达“进入作用域时获取资源，离开作用域时一定释放资源”。同步上下文管理器对应 `with`，核心方法是：

```python
class Resource:
    def __enter__(self) -> "Resource":
        # 获取资源，with ... as resource 得到这里的返回值
        return self

    def __exit__(self, exc_type, exc, traceback) -> None:
        # 无论 with 代码块正常结束还是抛出异常，都会进入这里
        self.close()

    def close(self) -> None:
        # 释放同步资源
        ...


with Resource() as resource:
    ...
```

异步资源需要等待才能完成清理时，应使用 `async with`、`__aenter__`、`__aexit__` 和 `aclose()`：

```python
from types import TracebackType
from typing import Self


class AsyncResource:
    async def __aenter__(self) -> Self:
        return self

    async def __aexit__(
        self,
        exc_type: type[BaseException] | None,
        exc: BaseException | None,
        traceback: TracebackType | None,
    ) -> None:
        await self.aclose()

    async def aclose(self) -> None:
        ...


async with AsyncResource() as resource:
    ...
```

这些方法的职责不同：

| 方法 | 调用方式 | 主要职责 |
|---|---|---|
| `close()` | `resource.close()` | 显式释放同步资源 |
| `aclose()` | `await resource.aclose()` | 显式释放需要异步等待的资源 |
| `__enter__()` | 进入 `with` 时自动调用 | 准备资源并返回上下文中的对象 |
| `__exit__()` | 离开 `with` 时自动调用 | 调用同步清理逻辑并处理异常传播 |
| `__aenter__()` | 进入 `async with` 时自动调用 | 异步准备资源并返回上下文中的对象 |
| `__aexit__()` | 离开 `async with` 时自动调用 | 等待异步清理并处理异常传播 |

`close()` / `aclose()` 是显式清理 API，上下文管理器方法是围绕它们提供的作用域语法。通常应把真正的清理逻辑集中在 `close()` 或 `aclose()`，让 `__exit__()` 或 `__aexit__()` 调用它，避免维护两套清理代码。

一般情况下，`__exit__()` 和 `__aexit__()` 返回 `None` 或 `False`，让业务异常继续向外传播。返回 `True` 会吞掉 `with` 代码块中的异常，除非类的明确职责就是处理该异常，否则不应这样做。

##### 哪些类应该实现这些方法

满足以下条件之一时，适合提供 `close()` / `aclose()`，并通常同时支持上下文管理器：

1. 类自己创建并持有必须释放的资源，例如 HTTP 客户端、文件句柄、数据库连接、临时目录、锁或后台任务。
2. 调用方需要一个清晰、确定的资源作用域，例如“只在一次请求中存活”或“只在一个批处理任务中存活”。
3. 资源释放需要在异常发生时同样得到保证。
4. 一个对象组合了多个需要按顺序关闭的子资源。资源较多时，可以考虑标准库 `ExitStack` 或 `AsyncExitStack`。

例如，当前 `OpenAIProvider` 在没有传入客户端时会自行创建 `AsyncOpenAI`，因此它需要实现异步清理能力：

```python
class OpenAIProvider:
    def __init__(self, client: AsyncOpenAI | None = None) -> None:
        self._owns_client = client is None
        self._client = client or AsyncOpenAI(...)

    async def __aenter__(self) -> "OpenAIProvider":
        return self

    async def __aexit__(self, exc_type, exc, traceback) -> None:
        await self.aclose()

    async def aclose(self) -> None:
        if self._owns_client:
            await self._client.close()
```

这里最重要的是 `_owns_client`：

- Provider 自己创建客户端，Provider 拥有该资源，退出时应该关闭；
- 客户端由外部依赖注入，资源所有权属于外部，Provider 不应该关闭它；
- 应用级客户端由 FastAPI lifespan 创建时，也应该由同一个 lifespan 关闭。

这就是“谁创建，谁关闭”的资源所有权原则。对象可以使用外部资源，但使用不等于拥有。

##### 哪些类不应该实现这些方法

以下对象通常不需要 `close()` 或上下文管理器：

1. 只保存普通数据的 Pydantic 模型、dataclass、DTO 和配置对象。
2. 不持有外部资源的无状态业务服务。
3. 只引用外部注入资源、但不拥有该资源的轻量包装器。
4. 工具注册表、纯函数集合等没有清理动作的对象。
5. 仅仅为了让 API “看起来统一”，但退出时实际上无事可做的类。

例如 `AgentContext` 只保存当前请求的 `owner_id`，`ToolRegistry` 只保存工具定义，它们没有需要释放的资源，不应实现空的 `close()`、`__enter__()` 或 `__aenter__()`。

不要用 `__del__()` 代替显式关闭或上下文管理器。对象何时被垃圾回收并不确定，解释器退出时依赖对象也可能已经被销毁，因此 `__del__()` 不适合承担网络连接、事务或文件写入等关键清理工作。

##### 如何选择同步还是异步版本

- 清理过程只有普通内存操作或同步系统调用：使用 `close()`，需要作用域语法时实现 `__enter__()` / `__exit__()`。
- 清理过程需要 `await`，例如关闭异步 HTTP 客户端、等待后台任务退出：使用 `aclose()` 和 `__aenter__()` / `__aexit__()`。
- 一个类不应在 `__exit__()` 中临时启动事件循环去执行异步清理；在异步应用中直接提供异步上下文管理器。
- 如果第三方客户端已经支持 `with` 或 `async with`，优先直接组合它的上下文管理器，不必重复包装一套相同逻辑。

无论同步还是异步，关闭操作都应尽量可重复调用，避免正常退出和异常处理同时触发清理时产生二次关闭错误。关闭以后，也不应继续接受新的业务调用。

#### 3.1.2 SSE 与流式事件协议

`POST /api/v1/chat` 返回完整 JSON；`POST /api/v1/chat/stream` 返回 `text/event-stream`。请求体仍为 `message` 和可选的 `session_id`，鉴权仍使用 Bearer Token。前端使用 `fetch()` 发起 POST，再逐段读取响应；不能直接用只支持 GET 的原生 `EventSource` 替代当前调用方式。

一帧 SSE 以空行结束。`data` 中使用 JSON 序列化，正文中的换行变为 JSON 转义，不会破坏帧边界：

```text
event: text_delta
data: {"type":"text_delta","provider_item_id":"msg_1","delta":"第一行\n第二行"}

```

一次网络读取可能包含半帧、多帧或跨 UTF-8 字符的字节。浏览器应使用支持流式解码的 `TextDecoder`、保留未完成缓冲，并按空行解析，不能把每个网络 chunk 都当成完整 JSON。

| 事件 | 主要数据 | 发送时机 |
|---|---|---|
| `started` | `session_id`、`turn_id` | 用户输入和 Turn 的开始事务提交后 |
| `function_call` | `call_id`、`tool_name`、完整 `arguments` | 执行工具之前 |
| `function_call_output` | 同一 `call_id`、`output`、`succeeded`、`sources` | 得到工具结果之后；执行失败也会发送 |
| `text_delta` | `delta`、`provider_item_id`、`provider_response_id` | 收到模型文字增量时 |
| `completed` | 最终 `answer`、聚合 `retrieved_sources`、会话/轮次 ID | 保存事件并提交完成事务后 |
| `error` | 安全的 `code`、`message`、会话/轮次 ID | 响应开始后的业务失败 |

工具结果的 `output` 是字符串，通常是 JSON；如果前端需要展开结构，先解析 SSE 的外层 data，再按工具定义解析 output。用 `call_id` 关联调用与结果；用消息/响应 ID 区分工具循环中不同模型请求的文字，不应将所有增量无条件视为最终答案。以 `completed.answer` 校正最终展示。

路由先调用 `anext(events)` 读取开始事件，再返回响应。会话不存在等初始化错误仍可返回 HTTP 404；开始事件之后的预算、压缩或模型错误通过 SSE error 表达，HTTP 状态已不能从 200 改为 502。未收到 completed 的连接结束不能视为成功。

请求级数据库和 Provider 的 yield 依赖要存活到响应发送完成，当前使用默认 request scope；不要改为发送响应前就清理的 function scope。见 [FastAPI yield 依赖生命周期](https://fastapi.tiangolo.com/tutorial/dependencies/dependencies-with-yield/)。

#### 3.1.3 为什么自定义 `ChatStreamingResponse`

普通 `StreamingResponse` 已经能发送 SSE。当前自定义类在其外层补充完整响应生命周期的清理，并把编码、心跳和流内错误集中管理：

| 方法 | 职责 |
|---|---|
| `__init__()` | 保存已启动的会话生成器和 started，设置 SSE、no-cache 与代理缓冲提示 |
| `_body()` | 输出事件帧，等待新事件时发送心跳，将业务异常转为 error |
| `__call__(scope, receive, send)` | 调用父类发送响应，在 finally 中关闭响应体和会话生成器 |

`__call__` 是 ASGI 应用入口：`scope` 是连接元数据，`receive` 接收客户端消息，`send` 发送响应头和正文。它不是上下文管理器的 `__aenter__`，而是框架执行 `await response(scope, receive, send)` 时的入口。

预读 started 后，会话生成器已经启动。若发送 HTTP 响应头就失败，正文生成器可能还没有进入 `_body()`，只在正文里写 finally 不足以关闭会话。外层 `__call__()` 的 finally 覆盖首帧发送失败、正常结束和断开路径。关闭响应体会先清理等待任务，随后关闭会话，避免对仍在读取的异步生成器并发执行 `aclose()`。

`X-Accel-Buffering: no` 是代理缓冲提示，是否生效仍取决于代理；心跳也不能替代部署侧的超时配置。

#### 3.1.4 心跳、任务与取消传播

没有新业务事件时每 15 秒发送 `: ping\n\n`。它是 SSE 注释，不属于业务事件，不入库。当前通过一个 pending Task 等待 `anext(events)`：

```python
pending = asyncio.create_task(anext(events))
done, _ = await asyncio.wait([pending], timeout=15)
if not done:
    # 发送心跳，下次继续等待同一个 pending
    ...
```

`asyncio.wait()` 超时不会取消 pending；如果每次心跳都使用会取消被等待任务的超时方式并重新读取，就可能中断模型或工具执行。收到结果后读取 `task.result()`，再创建下一次读取任务；同一会话事件流最多有一个待完成读取。保持任务引用，并在断开时 cancel 后 await，避免后台任务泄漏。见 [Python asyncio 等待与取消](https://docs.python.org/3.12/library/asyncio-task.html#waiting-primitives)。

取消链路如下：

```text
前端 AbortController.abort() / 客户端断开
→ 停止响应发送，取消并等待 pending
→ Service 收到 CancelledError，或关闭生成器时收到 GeneratorExit
→ 关闭 Provider 与上游模型流
→ 保存已产生的完整事件，把未完成 Turn 标记 FAILED
→ 继续传播取消/关闭异常，释放请求级依赖
```

`CancelledError` 属于 BaseException，不能只靠 `except Exception` 捕获。`aclose()` 是关闭异步生成器的操作，不等同于停止远端模型计算；`aclosing()` 用作用域确保显式关闭。清理完成后继续传播取消异常，不把取消转换成正常 completed。

项目在清理期间使用 `with CancelScope(shield=True)`，抵御外层取消作用域对 await 的再次取消。它只保护收尾阶段，不让整个模型执行忽略取消，也不保证进程崩溃时可以完成入库。见 [AnyIO 取消屏蔽](https://anyio.readthedocs.io/en/stable/cancellation.html#shielding)。

前端可以用同一个 AbortController 的 signal 发起 fetch，并在用户停止生成时调用 abort。当前没有单独 cancel 接口或 cancelled 事件：连接已断开时无法再依赖该连接发送确认，后端关闭流也不保证供应商停止计费。

#### 3.2.1 模型流与业务流是两个层次

`OpenAIProvider.generate(..., stream=True)` 请求 Responses 流，并将供应商事件映射为项目事件。不开启 stream 时继续使用完整响应，摘要调用也保持非流式。

| 模型侧事件 | Provider 处理 |
|---|---|
| `response.created` | 记录本次响应 ID |
| `response.output_text.delta` | 立即 yield AssistantTextDeltaEvent，携带 item ID 和增量 |
| `response.completed` | 取得完整 Response，关闭本次流，读取 usage 和完整 output |
| `response.failed` / `response.incomplete` / `error` | 抛出 ModelResponseError；不把部分文字作为成功回答 |
| 无完成事件就结束 | 视为流意外结束 |

工具参数可能分多段到达。第一版不执行参数增量，而是等待完整 Response 中的 function_call，再解析完整 arguments、发出调用事件并执行工具。一次 `response.completed` 只表示本次模型请求完成；有工具调用时仍需追加对应 function_call_output，再发起后续请求，不能提前结束整个 Turn。见 [OpenAI 官方流式文档](https://developers.openai.com/api/docs/guides/streaming-responses)。

`AssistantMessageEvent` 用于完整消息入库，`AssistantTextDeltaEvent` 只用于实时传输；`ModelCompletedEvent` 是 Provider 的最终用量信息，Service 据此完成 Turn，HTTP 层再发送 ChatCompletedEvent。这些完成事件不能互相替代。

#### 3.3.1 `AsyncSession`、`begin()`、`flush()` 与 `commit()`

`AsyncSession` 是 SQLAlchemy 的工作单元和事务入口。项目中的 `get_db()` 只负责创建、产出和关闭请求级 Session：

```python
async def get_db():
    async with session_factory() as session:
        yield session
```

单独退出 `async with session_factory()` **不会自动提交业务写入**。如果代码只执行 `add()` 和 `flush()`，最后没有提交，Session 关闭时未提交的事务会被回滚。

项目使用 `AsyncSession.begin()` 表达事务作用域：

```python
async with db.begin():
    db.add(entity)
    await db.flush()
```

其行为是：

- 代码块正常退出：自动 `COMMIT`；
- 代码块抛出异常：自动 `ROLLBACK`，然后继续向上抛出异常；
- 因此不要在同一个 `begin()` 代码块里重复调用 `commit()` 或 `rollback()`。

`flush()` 与 `commit()` 的职责不同：

| 操作 | 作用 | 是否结束事务 | 当前项目由谁调用 |
|---|---|---:|---|
| `add()` / `add_all()` | 把 ORM 对象加入当前 Session | 否 | Repository |
| `flush()` | 把待执行 SQL 发送到数据库，获得约束检查和数据库生成值 | 否 | Repository |
| `commit()` | 永久提交当前事务 | 是 | `begin()` 上下文管理器或业务 Service |
| `rollback()` | 撤销当前事务尚未提交的变更 | 是 | `begin()` 异常路径或显式错误处理 |

不用 `begin()` 时必须显式提交：

```python
db.add(entity)
await db.commit()
```

但项目的会话写入统一使用 `begin()`，让正常提交和异常回滚保持对称。

#### 3.3.2 Repository 参与事务，但不拥有事务

Repository 只封装查询和持久化语句，不决定业务事务边界：

```python
@dataclass
class ConversationRepository:
    _db: AsyncSession

    async def create_session(self, owner_id: str) -> Session:
        session = Session(owner_id=owner_id)
        self._db.add(session)
        await self._db.flush()
        return session
```

`ConversationService` 和 `ConversationRepository` 接收的是同一个 `AsyncSession` 实例：

```python
budget = ContextBudget.configured()
repository = ConversationRepository(db)
service = ConversationService(
    _db=db,
    _repository=repository,
    _provider=provider,
    _context_builder=ContextBuilder(summarizer=provider, budget=budget),
)
```

因此 Service 在 `db.begin()` 上开启的事务会自然覆盖 Repository 内部的 `add()`、`execute()` 和 `flush()`。Repository 不应自行 `commit()`，否则一个包含多个 Repository 操作的业务事务会被提前切断，后续步骤失败时无法整体回滚。

事务应由最了解完整业务步骤的 Service 或 API 用例层控制。`OpenAIProvider` 是供应商适配层，不持有 `AsyncSession` 或 Repository，也不负责数据库事务。

## 6. Markdown 采集与切块策略

扫描器使用 `Path.rglob("*.md", case_sensitive=False)` 递归查找 Markdown，并跳过 `.git`、`.venv`、pytest/Ruff 缓存、`__pycache__` 等目录。

切块过程分三层：

1. 标题分节：识别 1～6 级 ATX 标题，并维护完整标题路径。
2. 空行分段：把同一节拆成自然段；围栏代码块内部的 `#` 不会误判为标题。
3. 长度控制：单块默认不超过 500 字符，短段尽量合并，超长段按字符切分。

每个 Chunk 保存：确定性 UUID、文档 ID、顺序、标题级别、标题路径、正文、起止行号、SHA-256 哈希和创建时间。

## 7. Manifest 增量索引设计

Manifest 是 JSON 快照，记录：

- 知识库根目录；
- 文档 ID、内容哈希、大小、修改时间；
- Chunk ID、顺序、哈希、标题路径和行号；
- 切块器版本和最大 Chunk 长度。

`compare_manifests()` 将文件分为 `added`、`modified`、`deleted`、`unchanged`。如果切块配置变化，共有文件也会被标记为需要重建。当前 CLI 的 `plan` 只预览变化，不写 Manifest，也不修改向量索引。

| `turns` | `session_id`、`sequence`、`status`、模型信息、token 用量、最终 Response ID | 保存一次用户输入到最终回答的完整执行状态 |
| `conversation_items` | `turn_id`、`sequence`、`item_type`、`role`、`call_id`、`payload` | 按顺序保存消息、工具调用、工具结果等会话项 |

数据库使用外键级联删除、唯一约束、检查约束和普通索引。向量索引为 HNSW，操作符类为 `vector_cosine_ops`。

`IndexService` 的一次索引操作依次执行：校验 Chunk 归属 → 批量 Embedding → 校验数量 → 替换 Chunk → Upsert 向量。事务提交由 API 路由统一负责，仓储层只 `flush()`，便于把文档状态、Chunk 和向量放进同一事务。

### 8.1 文档、Chunk 与向量关系

知识库数据关系如下：

```text
Document 1 ── N Chunk
Chunk    1 ── 1 VectorRecord
```

- 删除 Document 时通过 `ON DELETE CASCADE` 删除对应 Chunk；
- 删除 Chunk 时级联删除对应 VectorRecord；
- `(document_id, sort_index)` 唯一，保证同一文档内的切块顺序不重复；
- `vectors.chunk_id` 同时是主键和外键，保证一个 Chunk 只有一条当前向量；
- 重新索引时 Chunk 使用替换写入，向量使用 PostgreSQL Upsert。

### 8.2 Session、Turn 与 ConversationItem

Agent 会话采用三层结构：

```text
Session
└── Turn
    ├── ConversationItem：user message
    ├── ConversationItem：compaction（需要压缩时的摘要检查点）
    ├── ConversationItem：reasoning（表结构预留，当前尚未产生）
    ├── ConversationItem：function_call
    ├── ConversationItem：function_call_output
    └── ConversationItem：assistant message
```

概念边界：

- `Session` 是产品内的长期会话，通过 `owner_id` 做用户隔离；它不是 OpenAI Conversation；
- `Turn` 是一次用户输入开始、经过零到多次模型/工具调用、到最终回答结束的完整业务过程；
- `ConversationItem` 是 Turn 内有序的消息或动作，`(turn_id, sequence)` 唯一；
- `call_id` 用于配对 `function_call` 和 `function_call_output`；
- `text_content` 是常用文本投影，便于会话展示和查询；
- `payload JSONB` 保存供应商响应 ID、工具参数、执行状态和来源引用等结构化数据；
- `created_at` 用于审计，不承担严格排序；严格执行顺序必须使用 `sequence`。

当前 MVP 不建立 `model_responses` 表。成功回答过程中多次 `responses.create()` 返回的 usage 累加到 Turn；摘要调用和失败轮次已发生的调用用量目前未完整记录，`final_provider_response_id` 只保存最后一次 Response ID。未来需要逐次模型调用成本、状态和故障恢复时，再增加 `ModelResponse` 层。

### 8.3 会话问答的短事务与事件发送顺序

数据库事务不跨越外部模型请求。普通 `chat()` 和流式 `chat_stream()` 共用 `_chat_events()` 编排，Repository 只查询、写入和 `flush()`：

```text
开始事务：创建/锁定 Session → 创建 Turn → 加载历史 → 保存当前用户消息 → COMMIT
  ↓
发送 started：此时客户端已能获得 session_id 和 turn_id
  ↓
事务外：构建上下文，必要时调用模型分批生成历史摘要
  ↓
可选摘要事务：保存 Compaction Item 和覆盖边界 → COMMIT
  ↓
事务外：模型流 → 工具调用 → 限制工具结果 → 后续模型流
        实时发送 function_call、function_call_output 和 text_delta
  ↓
结束事务：保存完整事件 → 更新用量和 Turn.completed → COMMIT
  ↓
发送 completed：携带最终回答与聚合来源
```

成功请求通常有开始和结束两段短事务；发生压缩时额外增加摘要事务。摘要先于后续回答入库，因此回答失败后仍可恢复已有摘要。文字增量用于显示，不逐条写数据库；完整工具事件和助手消息在结束或失败收尾时写入。

失败或取消时，开始事务已提交，Service 保存已有完整事件，并把未完成 Turn 标记为 `failed`。工具执行异常通常先转换为 `succeeded=False` 的工具结果，供模型继续处理，不必直接导致整轮失败；模型异常、预算不足或工具次数超限等则可以终止本轮。

`CancelledError` 和 `GeneratorExit` 要显式处理；只捕获 `Exception` 不能覆盖它们。当前实现关闭 Provider 生成器，并在 `CancelScope(shield=True)` 中执行失败收尾，之后继续传播原异常。回滚可能使 ORM 属性过期，因此缓存 `turn_id` 和 `session_id`，避免收尾或响应时隐式读取数据库。进程被强制终止不保证这些清理代码执行，不能把请求取消处理等同于崩溃恢复。

### 8.4 为什么 Conversation 和搜索使用不同的 `AsyncSession`

FastAPI 默认缓存同一个依赖函数的返回值，因此同一请求中的多个 `Depends(get_db)` 通常共享一个 `AsyncSession`。SQLAlchemy 查询也会触发自动开始事务：如果搜索工具与会话持久化共用 Session，向量查询产生的隐式事务可能跨越后续模型请求，并导致第二个显式 `begin()` 遇到“事务已经开始”。

Conversation 写事务与搜索查询应使用两个独立 Session。仅在同一个依赖函数上设置 `use_cache=False` 不能稳定表达这种资源边界：它要求 FastAPI 重新执行该依赖，但当前版本仍可能把首次求得的结果写入依赖缓存，使后续普通 `Depends(get_db)` 受解析顺序影响而复用它。

因此可靠做法是定义两个不同的依赖函数，让它们拥有不同的依赖缓存键：

```python
DatabaseSession = Annotated[
    AsyncSession,
    Depends(get_db),
]


async def get_conversation_db():
    async with session_factory() as session:
        yield session


ConversationDatabaseSession = Annotated[
    AsyncSession,
    Depends(get_conversation_db),
]
```

依赖关系为：

```text
ConversationService
├── conversation_db
└── ConversationRepository(conversation_db)

OpenAIProvider
└── ToolDependencies
    └── SearchService
        └── search_db
```

`ConversationService._db` 与 `ConversationRepository._db` 必须是同一个对象，保证 Repository 写入参与 Service 开启的事务；`search_db` 则必须是另一个请求级 Session，负责 pgvector 查询。`OpenAIProvider` 本身没有数据库 Session。

当前代码已经使用独立的 `get_conversation_db()`，并通过依赖测试断言 Conversation 与普通请求依赖拿到的 `AsyncSession` 不是同一个对象。

### 8.5 顺序、并发和锁

同一个 Session 的 Turn 使用 `(session_id, sequence)` 唯一约束。继续已有会话时，Repository 使用 `SELECT ... FOR UPDATE` 锁定 Session 行，再读取当前最大 Turn sequence 并创建下一条 Turn，避免两个并发请求为同一会话分配相同序号。

同一个 Turn 内的 Item 当前由 Agent 串行追加，使用 `(turn_id, sequence)` 保证顺序。以后支持并行工具时，仍应使用 `call_id` 建立调用与结果的对应关系，不能只依赖完成时间。

### 8.6 数据库初始化与增量迁移

- `migration/init_sql`：初始化全新数据库，创建 pgvector 扩展和当前全部表；
- `migration/001_create_chunks_and_vectors.sql`：为旧数据库增加 Chunk 和 Vector 表；
- `migration/002_create_agent_conversations.sql`：增加 Session、Turn 和 ConversationItem 表。

增量迁移文件只负责改变数据库结构，不代替 ORM 模型；`db/models.py` 与 SQL migration 必须同步维护。当前项目尚未引入 Alembic，因此执行过哪些 SQL 需要由部署流程自行记录，并且不要对同一数据库重复执行无幂等保护的迁移。

## 9. 架构与设计模式

### 9.1 应用工厂与路由分层

`create_app()` 统一创建 FastAPI 应用并挂载各业务路由，测试可以为每个用例创建独立应用。

### 9.2 依赖注入

FastAPI `Depends` 注入数据库会话、JWT Claims、请求级上下文和业务 Service。应用级的 embedding provider 由 `lifespan` 创建并保存到 `app.state`，再通过 `Request` 和依赖函数注入；测试可用 `app.dependency_overrides` 替换这些依赖，不需要真实 PostgreSQL 或 OpenAI。

### 9.3 Protocol / 依赖倒置

索引核心只依赖四个最小接口：可索引文档、Embedding Provider、Chunk Store、Vector Store。`PostgresChunkStore`、`PostgresVectorStore` 和 `InMemoryVectorStore` 都可按接口替换。

### 9.4 数据与向量分离

正文和结构化元数据放在 `chunks`，`vectors` 只存向量和模型名。这样能避免在向量表重复正文，也便于更换 Embedding。

### 9.5 完整请求与上下文预算

一次模型请求包含 `model`、`instructions`、`input`、`tools` 和 `max_output_tokens` 等字段。`ContextBuilder.build()` 返回 instructions、按顺序排列的消息、估算输入长度及可选压缩检查点；它不负责构造模型客户端、调用网络、执行工具或提交数据库事务。

初始 input 的顺序是“已有摘要（若有）→ 未覆盖的历史用户/助手消息 → 当前用户消息”。当前问题只追加一次，instructions 不混入普通消息。工具定义也占请求输入；Provider 在工具循环中继续追加模型 output 和配对的 function_call_output。

配置按最小原则提供：

| 配置 | 默认值 | 含义 |
|---|---:|---|
| `CHAT_CONTEXT_WINDOW` | 32768 | 用户根据模型服务设置的最大上下文容量，不是自动识别结果 |
| `CHAT_CONTEXT_BUDGET` | 32768 | 应用单次请求总预算，必须不超过模型容量 |

输出预留、安全余量、工具预留和单次工具结果上限采用代码默认值，不要求普通使用者调节所有参数。对于预算 T，当前默认输出预留为 `min(8192, max(1, T // 4))`，安全余量为 `min(4096, T // 8)`，工具预留为 `min(8192, T // 8)`：

```text
完整输入上限 input_tokens = T - 输出预留 - 安全余量
初始输入上限 initial_input_tokens = input_tokens - 工具预留
```

T 为 32768 时，输出预留 8192、安全余量 4096、工具预留 4096，完整输入上限为 20480，Builder 构建上限为 16384。Provider 检查包含工具交互的完整请求时使用 20480；若继续使用 16384，预留空间就始终无法被工具使用。

当前计数是启发式估算：文本 ASCII 字符数除以 3 后向上取整，非 ASCII 字符每个计 1；消息和工具以紧凑 JSON 估算，并增加结构开销。它不是按供应商 tokenizer 精确计数，也不等于请求 JSON 的服务器实际计费规则。不同供应商、不同模型甚至同厂商不同模型可能使用不同 tokenizer，不能把厂商名作为精确计数的充分依据。

响应中的 usage 用于成功 Turn 的调用用量统计，尚未用于校准输入估算。把历史 Turn.total_tokens 相加不能算出本次上下文长度：之前的调用重复包含历史、系统规则、工具定义及输出，而本次请求只包含当前实际选入的内容。检索 Embedding 用量是另一种模型操作，不用于计算聊天上下文容量。

### 9.6 历史压缩与 Compaction 检查点

Builder 超过初始输入预算时，先检查 instructions、tools 与当前用户输入本身能否放下；固定部分已经超限时返回 InputTooLarge，不尝试压缩当前问题。历史按 Turn 分组，从最近一组开始保留，避免随意拆开问答。

较早历史通过 `compact_history()` 分批调用同一个聊天模型生成摘要；每批把已有摘要和新增历史合并，单条历史过长时按文本切分。压缩请求不调用检索工具。摘要保留用户目标、约束、修正、讨论进度和未完成事项，并把历史视为待总结数据，不执行其中的指令。

比例是软预算，当前摘要目标为 `min(2048, 可用于历史的空间 // 4)`，近期历史目标不超过该空间的一半，并扣除摘要包装开销。不是各部分超过某个百分比就分别压缩；触发条件是整个初始请求超限，压缩对象是较早历史，最后再次检查完整构建结果。

摘要不覆盖原始记录，而是写入独立 `ItemType.COMPACTION`。检查点包含摘要文本和 `covered_through_turn_id`；Repository 读取最新摘要，再加载覆盖边界之后的历史，避免把已摘要内容全部重复送入模型。它存放在当前 Turn 下，覆盖边界通常指向更早的历史 Turn。

历史恢复包括已完成问答，以及失败 Turn 的用户消息。失败轮次的工具轨迹和助手消息不作为普通历史恢复，以便用户说“继续”时还能看到此前的问题，同时避免不完整输出干扰上下文。摘要只属于当前会话，不自动混入其他会话或长期记忆。

### 9.7 工具结果限制与来源一致性

历史压缩调用模型生成摘要；工具输出限制采用结构化筛选和正文截断，不调用模型总结，两者是不同处理。

Provider 在追加完整模型 output 后计算剩余输入容量。`ToolOutputBudget` 表示单个 function_call_output 的可用容量，计入 call_id、包装结构及结果字符串的 JSON 转义开销。同批多个调用先各预留最小有效错误结果空间，再分配额外容量；单个结果通常最多约 2048 个估算 Token，小预算下自动降低。工具预留是初始空间，不是每次调用可重新领取的额度，多次检索均按实际余额计算。

SearchKnowledgeTool 的处理顺序：

1. 全部结果能放下时，保留原始结果。
2. 放不下时按 score 从高到低尝试保留完整片段；过大的片段可以跳过，继续尝试较小片段。
3. 一个完整片段都放不下时，二分查找最高分片段能容纳的正文前缀，追加截断提示，清除原 end_line。
4. 限制后的结果用 `results` 和 `truncated: true` 表明资料不完整，同时 sources 只保留实际送入模型的片段及正文。
5. 连来源元数据与少量正文都放不下时明确报错，不把预算不足伪装成“没有检索结果”。

不能直接截断序列化 JSON 的字符串，否则会破坏结构、转义或来源字段。Provider 对工具返回值再次校验，未遵守预算的工具仍会失败。SSE 与数据库中的工具结果均来自同一结果事件，前端看到的来源应与模型看到的内容一致。

### 9.8 事件、持久化与用量的边界

| 层次 | 负责内容 | 不负责内容 |
|---|---|---|
| ContextBuilder / Compactor | 选择历史、估算、生成摘要及覆盖边界 | 网络传输格式、数据库提交 |
| Provider / ToolRegistry | 模型流、工具执行、工具容量和模型 usage | 会话归属、SSE 编码、数据库事务 |
| ConversationService | 创建 Turn、保存摘要和完整事件、聚合来源、完成或失败收尾 | 供应商事件细节、HTTP 错误状态 |
| ChatStreamingResponse / 路由 | 预读开始事件、SSE 编码、心跳、安全错误、断开清理 | 工具检索策略、历史压缩策略 |

一次用户请求可以包含多次模型请求；一次模型请求可以产生多个工具调用；一次文本消息会产生多个增量。Turn、Response、工具调用、完整消息和 delta 是不同粒度，不能都用“完成”表示。

## 11. 当前实现边界与注意事项

以下边界根据当前源码判断，已讨论的后续能力不视为已实现：

1. **Token 计数仍是估算。** 没有按模型选择精确 tokenizer，也没有用响应 usage 校准后续输入估算；模型容量需按实际服务设置。
2. **摘要超长还没有再次压缩机制。** 模型生成上限和本地估算口径不同，正常结束的摘要仍可能被判超长；为空、未减少长度或超限时当前直接失败。
3. **用量统计不完整。** 普通回答成功时聚合模型调用 usage；摘要调用和失败轮次的已发生调用用量尚未完整入库，不包含检索 Embedding 用量。
4. **工具预算不是无限容量保证。** 检索结果可以筛选或截断，无法放入最小有效结果时仍报错；不压缩本轮正在执行的工具轨迹。
5. **历史恢复有明确范围。** 恢复当前会话的最新摘要、未覆盖的已完成问答和失败轮次的用户消息；不跨会话注入历史，不重放旧工具轨迹，不持久化 reasoning。
6. **取消以连接断开实现。** 没有独立 cancel API、`cancelled` 事件、任务持久化队列或崩溃后自动恢复；关闭模型流不保证供应商立即停止计算或计费。
7. **SSE 没有断点续传。** 不提供事件 ID、重连 replay 或去重协议；客户端应处理流内 error，并使用最终 completed.answer 校正展示结果。
8. **同会话 Turn 并发暂不支持。** 行锁保护序号分配，但不覆盖整个模型执行过程，不代表同时提交的问题能看到对方的回答。
9. **索引失败状态可补强。** 当前索引路径未专门记录失败状态；向量维度默认与表结构均为 1536，更换 Embedding 时仍须同步配置和数据库列。
10. **DTO、迁移和依赖管理可完善。** 文档列表返回 30 字符预览，仍使用 Document 模型；迁移尚无 Alembic 跟踪。Pydantic、pydantic-settings、Starlette 和 AnyIO 有直接导入但由传递依赖安装。
11. **配置在导入时实例化。** `config = Settings()` 要求环境变量准备就绪；Conversation 与检索使用不同请求级 AsyncSession，新增依赖时保持这一边界。

## 13. 建议阅读顺序

先从 `api/routes/ai.py` 看 HTTP 请求如何变成 SSE，再沿 `ConversationService._chat_events()` 理解数据库事务与业务事件，接着阅读 `OpenAIProvider.generate()` 的模型流和工具循环。最后对照 `context/budget.py`、`builder.py`、`compactor.py` 和 `tools/search_knowledge.py`，区分请求预算、历史摘要和检索结果裁剪。
