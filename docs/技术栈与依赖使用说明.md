# Interview AI 技术栈与依赖使用说明

> 审计范围：`pyproject.toml`、`uv.lock`、`src/interview_ai`、`tests`、数据库迁移脚本与现有项目文档  
> 审计时间：2026-09-11  
> 当前版本：`0.1.0`；最近提交：`7c8029b feat(indexing): 引入 pgvector 并实现文档分块索引持久化`

## 1. 项目概览

该项目是一个面向技术面试资料的 Python AI 后端。目前已经形成以下主链路：

1. 扫描本地 Markdown 文件，读取文件元数据与正文。
2. 按 Markdown 标题、段落和最大字符数切块。
3. 用 OpenAI Embedding API 批量生成向量。
4. 将文档、Chunk 和向量写入 PostgreSQL + pgvector。
5. 通过 pgvector 的余弦距离完成向量检索；同时保留内存向量库用于测试。
6. 通过 FastAPI 暴露文档上传、列表、索引与健康检查接口。
7. 使用 JWT Bearer Token 区分用户数据。
8. 使用 Typer 提供扫描与索引变更预览 CLI。

从代码结构看，项目采用 `src` 布局，并按 `api`、`db`、`ingestion`、`indexing`、`core` 分层。Embedding、Chunk 存储与向量存储通过 `Protocol` 抽象，核心索引服务依赖接口而不是具体实现，便于测试和替换基础设施。

### 3.1 FastAPI

当前用法覆盖应用工厂、路由拆分、依赖注入、鉴权、文件上传、错误响应和响应模型。

```python
from fastapi import APIRouter, Depends, File, UploadFile, status

router = APIRouter(prefix="/api/v1/documents", tags=["document"])


@router.post("", status_code=status.HTTP_201_CREATED)
async def add_document(
    file: Annotated[UploadFile, File(description="UTF-8 Markdown 文件")],
    claims: Annotated[dict[str, object], Depends(verify_bearer)],
    db: Annotated[AsyncSession, Depends(get_db)],
) -> Document:
    content_bytes = await file.read(5 * 1024 * 1024 + 1)
    ...
```

常见扩展用法：

```python
from pydantic import BaseModel


class ErrorResponse(BaseModel):
    detail: str
    request_id: str


@router.get(
    "/{document_id}",
    responses={404: {"model": ErrorResponse}},
)
async def get_document(document_id: UUID, db: DatabaseSession): ...
```

已注册的接口：

| 方法 | 路径 | 作用 | 鉴权 |
|---|---|---|---|
| GET | `/` | 示例根路由 | 否 |
| GET | `/health` | 健康检查 | 否 |
| GET | `/api/v1/documents` | 获取当前用户文档列表 | Bearer JWT |
| POST | `/api/v1/documents` | 上传 UTF-8 Markdown，最大 5 MiB | Bearer JWT |
| POST | `/api/v1/index?document_id=...` | 为指定文档切块并建立向量索引 | Bearer JWT |
| GET | `/api/v1/test/` | 鉴权连通性测试 | Bearer JWT |

`FastAPI(...)` 只在 `IS_DEBUG=true` 时开启 `/docs` 和 `/redoc`。

from openai import OpenAI

client = OpenAI(api_key=config.api_key, base_url=config.host)
response = client.embeddings.create(
    model=config.embedding_model_name,

### 3.3 SQLModel 与 SQLAlchemy 2.x

`SQLModel` 用于声明 `Document`、`Chunk`、`VectorRecord` 三张表；更细粒度的 PostgreSQL 类型、约束和索引由 SQLAlchemy 提供。

```python
class Document(SQLModel, table=True):
    __tablename__ = "documents"

    id: UUID = Field(default_factory=uuid7, primary_key=True)
    owner_id: str = Field(sa_column=Column(String(128), nullable=False))
    content: str = Field(sa_column=Column(Text, nullable=False))
```

异步引擎与 FastAPI 会话依赖：

```python
engine = create_async_engine(config.database_url, echo=config.is_debug)
session_factory = async_sessionmaker(bind=engine, expire_on_commit=False)


async def get_db():
    async with session_factory() as session:
        yield session
```

常见查询与写入：

```python
# 查询
stmt = select(Document).where(Document.owner_id == owner_id)
documents = list((await db.scalars(stmt)).all())

# 删除并刷新某文档的所有 Chunk；flush 但不自行 commit
await db.execute(delete(Chunk).where(Chunk.document_id == document_id))
db.add_all(chunks)
await db.flush()
```

PostgreSQL Upsert：

```python
stmt = insert(VectorRecord).values(values)
stmt = stmt.on_conflict_do_update(
    index_elements=[VectorRecord.chunk_id],
    set_={
        "vector": stmt.excluded.vector,
        "embedding_model": stmt.excluded.embedding_model,
        "updated_at": func.now(),
    },
)
await db.execute(stmt)
```

### 3.4 pgvector

向量表使用 `VECTOR(1536)`，并创建 HNSW 余弦索引：

```python
vector: list[float] = Field(sa_column=Column(VECTOR(1536), nullable=False))

Index(
    "ix_vectors_vector_hnsw",
    "vector",
    postgresql_using="hnsw",
    postgresql_ops={"vector": "vector_cosine_ops"},
)
```

相似度搜索把“余弦距离”转换为“分数”：

```python
distance = VectorRecord.vector.cosine_distance(query_vector)
stmt = (
    select(VectorRecord.chunk_id, distance.label("distance"))
    .order_by(distance)
    .limit(limit)
)
rows = (await db.execute(stmt)).all()
results = [
    SearchResult(chunk_id=chunk_id, score=1.0 - float(value))
    for chunk_id, value in rows
]
```

测试环境另有 `InMemoryVectorStore`，使用纯 Python 计算余弦相似度，适合隔离数据库进行单元测试。

### 3.5 PyJWT 与 Bearer 鉴权

项目使用 `HS256`，强制 Token 包含 `sub` 和 `exp`：

```python
JWT_ALGORITHM = "HS256"

token = jwt.encode(
    {"sub": "user-001", "exp": datetime.now(UTC) + timedelta(seconds=300)},
    secret,
    algorithm=JWT_ALGORITHM,
)

claims = jwt.decode(
    token,
    secret,
    algorithms=[JWT_ALGORITHM],
    options={"require": ["exp", "sub"]},
)
```

FastAPI 中用 `HTTPBearer(auto_error=False)` 读取凭证，再把无 Token、无效 Token 和过期 Token 统一转换成带 `WWW-Authenticate: Bearer` 的 401 响应。

### 3.8 uuid6

`Document.id` 使用 UUIDv7，适合数据库主键：保持 UUID 的分布式生成能力，同时比完全随机 UUID 更有时间局部性。

```python
from uuid6 import uuid7

id: UUID = Field(default_factory=uuid7, primary_key=True)
```

Chunk 则使用标准库 `uuid5()`，由“文档 ID + 顺序 + 内容哈希”确定性生成；相同输入可得到相同 Chunk ID。

## 6. Markdown 采集与切块策略

扫描器使用 `Path.rglob("*.md", case_sensitive=False)` 递归查找 Markdown，并跳过 `.git`、`.venv`、pytest/Ruff 缓存、`__pycache__` 等目录。

切块过程分三层：

1. 标题分节：识别 1～6 级 ATX 标题，并维护完整标题路径。
2. 空行分段：把同一节拆成自然段；围栏代码块内部的 `#` 不会误判为标题。
3. 长度控制：单块默认不超过 500 字符，短段尽量合并，超长段按字符切分。

每个 Chunk 保存：确定性 UUID、文档 ID、顺序、标题级别、标题路径、正文、起止行号、SHA-256 哈希和创建时间。

## 7. Manifest 增量索引设计

Manifest 是 JSON 快照，记录：

- 知识库根目录；
- 文档 ID、内容哈希、大小、修改时间；
- Chunk ID、顺序、哈希、标题路径和行号；
- 切块器版本和最大 Chunk 长度。

`compare_manifests()` 将文件分为 `added`、`modified`、`deleted`、`unchanged`。如果切块配置变化，共有文件也会被标记为需要重建。当前 CLI 的 `plan` 只预览变化，不写 Manifest，也不修改向量索引。

## 8. 数据模型与数据库能力

| 表 | 关键字段 | 作用 |
|---|---|---|
| `documents` | `owner_id`、`content`、`content_hash`、`status`、`chunk_count`、时间字段 | 保存上传文档和索引状态 |
| `chunks` | `document_id`、`sort_index`、`headings`、`content`、行号、哈希 | 保存可追溯的 Markdown 片段 |
| `vectors` | `chunk_id`、`vector`、`embedding_model` | 保存 Embedding；与 Chunk 一对一 |

数据库使用外键级联删除、唯一约束、检查约束和普通索引。向量索引为 HNSW，操作符类为 `vector_cosine_ops`。

`IndexService` 的一次索引操作依次执行：校验 Chunk 归属 → 批量 Embedding → 校验数量 → 替换 Chunk → Upsert 向量。事务提交由 API 路由统一负责，仓储层只 `flush()`，便于把文档状态、Chunk 和向量放进同一事务。

## 9. 架构与设计模式

### 9.1 应用工厂与路由分层

`create_app()` 统一创建 FastAPI 应用并挂载各业务路由，测试可以为每个用例创建独立应用。

### 9.2 依赖注入

FastAPI `Depends` 注入数据库会话、JWT Claims 和 `IndexService`。测试通过 `app.dependency_overrides` 替换数据库与索引服务，不需要真实 PostgreSQL 或 OpenAI。

### 9.3 Protocol / 依赖倒置

索引核心只依赖四个最小接口：可索引文档、Embedding Provider、Chunk Store、Vector Store。`PostgresChunkStore`、`PGVectorStore` 和 `InMemoryVectorStore` 都可按接口替换。

### 9.4 数据与向量分离

正文和结构化元数据放在 `chunks`，`vectors` 只存向量和模型名。这样能避免在向量表重复正文，也便于更换 Embedding。

## 11. 当前实现边界与注意事项

以下内容根据当前源码判断，适合作为下一步开发检查表：

1. **向量维度需统一。** `.env.example` 和配置默认值是 256，但 ORM/SQL 迁移声明为 `VECTOR(1536)`。若实际生成 256 维向量，写入会失败。应统一配置、模型能力与数据库列维度。
2. **RAG 问答尚未落地。** 当前有采集、切块、Embedding 和向量搜索底座，但没有 `/chat`、引用组装、流式回答和拒答策略。
3. **索引接口尚未调用检索。** `PGVectorStore.search()` 已实现，但还没有对外搜索/问答端点使用它。
4. **错误状态处理可补强。** 索引失败时当前路由没有显式回滚并把文档状态置为 `failed`。
5. **API 响应模型可拆分。** 直接以 `Document` 作为响应可能返回完整文档正文；可单独定义列表/详情 DTO。
6. **调试输出需清理。** 上传和测试路由中仍有 `print(...)`，测试路由还保留多项未使用导入。
7. **质量门禁未全绿。** 测试已通过，但 Ruff Lint/Format 尚未通过。
8. **配置为导入时实例化。** `config = Settings()` 会在模块导入阶段要求必填变量存在；部署和工具脚本需要准备好 `.env`，测试则应明确覆盖配置。
9. **直接与间接依赖可进一步明确。** 源码直接导入了 `pydantic` / `pydantic-settings`，但它们没有显式列在顶层 dependencies 中；依赖 FastAPI/SQLModel 的传递安装会增加升级时的不确定性。

当前项目已经不是单纯的 FastAPI 骨架，而是一套具备明确分层的 RAG 数据底座：Markdown 采集与可追溯切块、增量 Manifest、OpenAI Embedding、PostgreSQL/pgvector 持久化、JWT 多用户隔离、CLI 与完整单元测试都已出现。下一阶段的重点不是再引入更多框架，而是统一向量维度、完成检索到回答的 RAG 链路、补齐失败事务与响应 DTO，并让 Ruff 质量门禁恢复全绿。
